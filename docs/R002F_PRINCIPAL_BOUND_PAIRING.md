# R002F Principal-Bound Pairing Authority

Status: **STAGED_NOT_EXECUTED**

Branch: `r002f-pairing-readiness-runtime`

## Purpose

The copied one-time VPS pairing link must bind to an authenticated ChatGPT/HMS
integration identity before remote control tools can be exposed. The model must
not become the authority for choosing that identity, and the resulting durable
control-session bearer token must not be returned to model-visible tool output.

This tranche adds a principal-bound pairing service on top of the existing
PairingReadinessRuntime, PairingSessionExchange and hardened ControlSessionStore.
It does not yet add an MCP server, public app endpoint, or remote control tool.

## Trusted principal boundary

`TrustedIntegrationPrincipal` represents identity supplied by the authenticated
app/MCP boundary. It is not a network/tool input schema and must never be
constructed from model-controlled fields such as `principal_id`, `subject`,
`namespace`, `principal_sha256` or `is_trusted`.

The raw principal subject is excluded from repr and is not persisted by this
tranche. Durable authority uses a domain-separated SHA-256 over the canonical
namespace + subject pair.

## Pairing-link handling

The model-facing input remains the copyable pairing link generated by the local
HMS-GPT-VPS tool.

The principal pairing service:

1. requires current PairingReadinessRuntime freshness for the exact managed
   instance;
2. reloads the encrypted PairingLinkLease authority;
3. constant-time compares the supplied link bytes to the exact encrypted lease
   link;
4. does **not** parse a bearer token from model input;
5. uses the raw pair token only from the encrypted lease authority;
6. derives a deterministic principal-specific exchange nonce;
7. consumes/recovers the pairing through the existing atomic
   PairingSessionExchange;
8. re-observes fresh authenticated Agent presence;
9. verifies the exact durable ControlSessionStore record;
10. publishes the principal/session binding to encrypted host storage;
11. re-observes readiness before returning a non-secret result.

The model-visible result contains only instance/session metadata, scopes and
expiry. It does not contain the raw control-session token.

## Deterministic principal exchange nonce

The exchange nonce is HMAC-derived from:

- the Bridge-held PairingExchangeKey;
- a domain separator;
- the principal SHA-256;
- the exact pair_id.

Therefore two principals derive different initial session identities from the
same one-time pairing grant.

If the first principal successfully consumes the grant, another principal cannot
recover that session: its deterministic session identity differs and no matching
durable ControlSessionStore record exists.

## Crash recovery after exchange commit

A crash can occur after the atomic pairing/session transaction commits but
before the encrypted principal binding is published.

The normal external PairingSessionExchange recovery window remains 60 seconds.
This tranche does not widen that public replay window and does not add a trusted
bypass to `PairingSessionExchange.exchange()`.

For internal recovery, the Bridge still owns all three authorities required to
reconstruct the expected initial grant:

- encrypted PairingLinkLease with the original pair token;
- Bridge PairingExchangeKey;
- deterministic principal-specific nonce.

The service may therefore derive the expected grant again after the public
recovery window, but accepts it only if the exact derived session record already
exists in the hardened ControlSessionStore and remains currently valid. Missing,
changed, rotated, revoked, expired or differently-derived session authority fails
closed.

## Encrypted principal binding

`PrincipalSessionBinding` stores:

- schema version;
- principal SHA-256;
- exact instance_id and pair_id;
- exact session_id/family_id;
- session token SHA-256;
- scopes;
- issued/expires timestamps;
- session epoch;
- raw session token.

The raw token is excluded from repr and is persisted only through the encrypted
binding secret store. The production `DpapiPrincipalBindingRegistry` uses the
existing current-user DPAPI/pinned-file primitive and derives file names only
from principal digest and SHA-256(instance_id). The configured binding root must
already be a trusted normal directory and may not traverse symlink/junction or
reparse redirects.

Binding load verifies the raw token digest and then verifies all binding metadata
against the exact durable ControlSessionStore record before the bearer token can
be used internally.

## Intended control topology

This tranche does not execute workspace/process actions on the physical host.
The next control-dispatch layer must preserve:

`supported ChatGPT/HMS app -> trusted principal binding -> Bridge session/scope gate -> signed durable Agent command queue -> outbound managed guest Agent -> guest policy/action runtime -> result -> Bridge`

Host-local `ControlActionRuntime` is not the Bridge execution target.

## Regression authority staged

`tests/test_r002f_principal_pairing.py` stages coverage for:

- idempotent same-principal pairing without returning the bearer token;
- wrong copied link rejection before pairing consumption;
- cross-principal rejection after one principal consumes the grant;
- recovery after a simulated crash more than 60 seconds after exchange commit
  when the exact durable session still exists;
- exact same-principal binding lookup;
- principal subject exclusion from repr;
- duplicate-key rejection in encrypted binding JSON.

These are source/regression artifacts only until an actual project test runner
executes them.
