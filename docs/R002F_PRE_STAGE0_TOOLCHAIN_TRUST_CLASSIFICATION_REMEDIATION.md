# R002F Pre-Stage0 Toolchain Trust Classification Remediation

Status: `STAGED_NOT_EXECUTED`.

## Finding

Fresh review of the project-manifest authoring path found that
`pin_reviewed_git_executable()` pins and hashes the `git.exe` file itself, but
does not prove the complete DLL/dependency closure used when that executable
runs.

That is the same trust-boundary class previously rejected for executable-only
Python/Git pinning: an exact executable hash is not equivalent to a sealed
runtime closure.

## Remediation in this revision

The legacy project-manifest authoring path is retained only as
defense-in-depth/observation tooling. It no longer claims that the generated
project manifest is externally approved.

`author_reviewed_project_manifest()` now returns:

- `external_approval_required=true`
- `external_approval_self_proven=false`

Runtime authoring already had the same classification.

No Hyper-V, Bridge, Agent, tunnel, or production command is executed by this
revision.

## Frozen production rule

No pre-stage0 Python/Git process may become the root of production deployment
authority merely by hashing its entrypoint executable.

Production qualification requires an independent external artifact authority for
project/Python/Git manifests, followed by independent bundle/command approval,
then the OS-backed launcher/stage-0 sealed-preflight chain.

The external authority may use the legacy Git-based checks as corroborating
evidence, but never as self-sufficient provenance.

## Consequence

Any project manifest generated by an older revision that reported
`external_approval_required=false` is stale for production authority purposes
and must be independently re-reviewed/pinned before use.

All live proof booleans remain false until real Windows sealed-preflight evidence
is independently accepted.
